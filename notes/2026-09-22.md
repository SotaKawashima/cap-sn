## 2. 当初の生成方針（現在は採用しない）

| 系列 | 3個のグラフの作り方 | 主な維持・監査条件 |
| --- | --- | --- |
| BA1000 | 同じBAモデル（$n=1000,m=10$）で生成シードを変える | 無向、元の`comm.csv`。次数分布、連結性、辺重複 |

`comm.csv`はユーザのsupport levelであり、組み替え制約に使う**コミュニティ分割そのものではない**。分割の作り方と乱数シードは生成前に固定する。FacebookとWiki-voteのsurrogateは元の観測グラフを組み替えたもので、独立に観測された別ネットワークとは呼ばない。BA1000のみ、同じ生成モデルからの別実現として扱える。

Facebookで次数だけを保って接続先を大きく変えると、クラスタリングやコミュニティ構造が崩れることは[9月18日の検討](2026-09-18.md)で確認済みである。一方、1%程度の組み替えは元グラフに近すぎる。指定した構造特性を保ちながら十分に辺を入れ替えられるかは、構造情報だけを使う生成pilotで確かめる。

生成手法の参照：[NetworkXのBAモデル](https://networkx.org/documentation/stable/reference/generated/networkx.generators.random_graphs.barabasi_albert_graph.html)、[graph-toolの制約付き組み替え](https://graph-tool.skewed.de/static/docs/stable/autosummary/graph_tool.generation.random_rewire.html)。

## 5. graph-toolによる構造pilot

- Homebrewの`graph-tool 3.8`をインストールし、Python 3.14で読み込みを確認した。既存の`.venv`にはインストールしていない。pilotではHomebrewのsite-packagesを実行時だけ`PYTHONPATH`に加えた。
- [pilotスクリプト](../scripts/pilot_similar_network_rewire.py)で、元グラフだけからNetworkX Louvain分割を固定した（分割seed `20260922`）。Facebookは16群、Wiki-voteは有向グラフの無向射影で31群。`comm.csv`を分割に使っていない。
- `constrained-configuration`モデルでノードごとの次数（Wiki-voteは入次数・出次数）と群間の辺数を厳密に維持した。自己ループ・重複辺を禁止し、Wiki-voteのシミュレータで使う向きを考慮して出力・再読込した。
- 各試作は元グラフから独立に作成した。辺数の5%、10%、25%、50%の交換試行、および1・3・10 sweepを比較した。これらは**組み替え試行回数**であり、実際の辺変更率ではない。

| 系列・条件 | 元辺との重複率 | Facebook平均クラスタリング | Facebook推移性 | Wiki-vote相互性 |
| --- | ---: | ---: | ---: | ---: |
| Facebook元 | 100.0% | 0.606 | 0.519 | - |
| Facebook 5%試行 | 96.4% | 0.551 | 0.504 | - |
| Facebook 10%試行 | 93.1% | 0.510 | 0.492 | - |
| Facebook 25%試行 | 84.1% | 0.432 | 0.464 | - |
| Facebook 1 sweep | 55.8% | 0.374 | 0.419 | - |
| Wiki-vote元 | 100.0% | - | - | 0.0565 |
| Wiki-vote 5%試行 | 93.5% | - | - | 0.0523 |
| Wiki-vote 10%試行 | 87.7% | - | - | 0.0482 |
| Wiki-vote 25%試行 | 72.5% | - | - | 0.0423 |
| Wiki-vote 1 sweep | 25.9% | - | - | 0.0294 |

全試作でノード・辺数、次数列、固定分割の群間辺数を検査し、Facebookの連結性は維持された。Wiki-voteの最大弱連結成分は元7066、試作で7064--7066、最大強連結成分は元1300、試作で1298--1318だった。Facebookの固定分割モジュラリティは全条件で元の0.835と同じだが、これは群間辺数を固定した結果であり、局所的な三角形の維持を意味しない。低い組み替え量では試作同士の辺重複も高い（Facebookの5%対10%で89.9%、Wiki-voteで82.1%）。

**暫定判断:** 単純な群・次数制約付き組み替えでは、元グラフと十分に異なる辺集合を得ようとすると、FacebookのクラスタリングやWiki-voteの相互性がかなり変わる。逆にこれらの指標を近づけようとすると元辺が多く残る。構造の許容幅と辺重複上限はまだ決めておらず、今回の試作を正式な類似グラフには採用しない。特に、固定したモジュラリティだけで「主要構造を維持した」とは主張しない。BA1000の別実現は今回まだ生成していない。

## 6. 別の観測グラフを使う方針への変更

組み替えグラフの構造を元に似せること自体を目的にせず、**同じ種類の別ネットワークでも、探索された良好な候補の位置や傾向が似るか**を確かめる。結果に合わせたグラフ選択を避けるため、出所・グラフの種類・元ネットワークに近いノード規模を先に基準とする。これは傾向の再現確認であり、構造要因の特定や他のネットワークへの一般化の証明ではない。

| 系列 | 現在の追加グラフ案 | 選ぶ根拠・留意点 |
| --- | --- | --- |
| BA1000 | 元と同じBAモデル（$n=1000,m=10$）で生成シードを変えた3個 | 同じ生成モデルの別実現。まだ正式生成していない。 |
| Facebook | [Brandeis99](https://networkrepository.com/socfb-Brandeis99.php)、[Bucknell39](https://networkrepository.com/socfb-Bucknell39.php)、[Rice31](https://networkrepository.com/socfb-Rice31.php) | Network Repository掲載の別々の大学のFacebook友人グラフ。掲載ノード数は順に約3,900、3,800、4,100で、元の4,039に近い。元の[SNAP ego-Facebook](https://snap.stanford.edu/data/ego-Facebook.html)とは収集単位・構造が異なり、同じFacebook由来というだけで「構造が近い」とは言わない。 |
| Wiki-vote | [SNAP wiki-RfA](https://snap.stanford.edu/data/wiki-RfA.html)の投票データから、元の[wiki-Vote](https://snap.stanford.edu/data/wiki-Vote.html)より後の期間を抽出 | 同じWikipedia管理者選挙の投票関係。元データは2008年1月まで、新データは2003年--2013年で期間が重なる。後続期間を優先し、規模が極端に小さい場合のみ全期間を再検討する。3個の別グラフへの分け方は未決定。 |

wiki-RfAの公式配布ファイルを取得し、**規模確認だけ**を行った。198,275票のレコードについて、`DAT`が解釈可能で2008年1月4日以降の票を取り出し、投票者から候補者への辺を作った。元のwiki-Voteが投票の有無を表すため、賛成・反対・中立を区別せず、同じ向きの重複辺と自己ループを除いた。この暫定規則では**約5,709ノード・79,476辺**だった。元の7,115ノード・103,689辺に対し、ノード数は約80%、辺数は約77%であり、「小さすぎる」とは判断しない。したがって現時点では全期間への切り替えは不要と考える。

ただし`DAT`を解釈できないレコードが9,371件あり、上記の規模には含めていない。2008年の開始年（`YEA`）だけで抽出すると1月1--3日の票が混じるため、元データとの期間の切り分けには使わない。公式ページの10,835ノード・159,388辺は**中立票を除いた全期間の別の集計**であり、今回の抽出値と直接比較しない。日付解釈、重複票の扱い、連結成分、元グラフとの重複、およびシミュレータ用のID・`comm.csv`の割り当ては実験前に確定・監査する。

Facebookの3データはこの時点では掲載値による仮選定だった。その後の実ファイルの確認と入力準備は7節に記す。従来の組み替えpilotや事前監査protocolはこの新方針の入力を生成するものではない。**夏休みの最適化で用いた元のwiki-Voteをwiki-RfA全期間版に置き換えて再実験するかは保留**し、今回の追加グラフ選定とは別に判断する。

## 7. 観測グラフの入力準備と連結性監査

Wiki-RfAは賛成・反対・中立のすべてを投票辺として扱い、重複した有向辺と自己ループを除いた。投票者名を昇順で0始まりのIDへ写し、元のwiki-Voteと同じく入力TOMLに`transposed = true`を指定した。`comm.csv`はこの新しいグラフから再計算した。元wiki-Voteと後続期間版を比較すると、最大弱連結成分は7,066/7,115から5,709/5,709、最大強連結成分は1,300/7,115から790/5,709、辺数/ノード数は14.57から13.92、相互性は0.0565から0.0546となった。**連結が壊れた形ではない**ため、現時点では全期間版へ切り替えない。ただし、入次数0の割合は約66.5%から79.3%へ変わり、構造が同一とは言えない。投票期間の変更自体が構造差を生む点を結果の解釈で明示する。

## 8. 追加実験①の実行範囲を確定

[9月21日の計画](2026-09-21.md)から、根拠の薄いWiki系列の追加2グラフを作らないことへ変更した。**追加グラフはBA1000系列3、Facebook系列3、Wiki-vote系列1の計7件**とする。BA1000とFacebookは3件ずつで傾向を比較するが、Wiki-voteについては後続期間版1件による確認に限り、同じ強さの再現性を主張しない。

| 項目 | 今回の実行仕様 |
| --- | --- |
| 対象 | 上記7グラフ。元の3グラフの第6段階最適化結果は比較用に再利用 |
| 目的関数 | 各グラフで累積利己的行動実行者割合$J_{\mathrm{cum}}$を最小化 |
| 設計変数 | 確実性・有効性を各0.5--1.0、適用値は小数第4位まで |
| 手法と最適化シード | BO-GP、CMA-ES、ランダムサーチ。各手法6シードで、第6段階と同じシード表を用いる |
| 評価予算 | 各最適化実行で50評価、各評価で100反復。BO-GPの初期評価10回は50回に含む |
| 探索用シミュレーションシード | **`30001`**。7グラフで番号を共通とし、第6段階の元グラフとの条件を揃える |
| 別枠の固定比較 | 各追加グラフで無介入と単純最大化$(1.0,1.0)$を、同じ`30001`で各100反復。最適化の50評価には含めない |
| 保存・固定条件 | 第6段階と同じ`pop`保存、介入の非探索条件と実行設定を原則維持。グラフ固有の`comm.csv`は7節の作成方法に従う |

追加グラフの最適化は$7\times3\times6=126$実行、計6,300評価・630,000シミュレーション反復となる。追加グラフの固定比較は$7\times2=14$実行・1,400反復。元の3グラフでも`30001`の無介入・単純最大化が必要なため、同条件で**固定比較6実行・600反復のみ**補う。元の第6段階の最適化はやり直さない。固定比較を含む新規実行の合計は146実行・632,000反復を予定する。

まずは各グラフで最適化点の散布図を作り、無介入・単純最大化と探索時の$J_{\mathrm{cum}}$を比べて、良好領域の位置や効果の傾向を確認する。**今回の実行は最適化と2固定条件の比較まで**とし、未使用シミュレーションシードでの追加検証は含めない。したがって探索時の1シード上の差を、未知シードでも安定した抑制効果や厳密な最適値の証明として扱わない。必要になった場合の独立検証は、この実験の後に別途設計する。

残る準備は、7グラフに対応する実行protocol・runner・分析手順の整備、新規入力の共用PCへの転送、短い試験実行による所要時間の再見積もりである。Facebookの新グラフは元より辺数が多いため、9グラフを前提とした従来の時間見積もりをそのまま使わない。

## 9. 実行直前の準備

上記8節の確定仕様を[実行protocol](../experiment_protocols/network_similarity_optimization_v1.json)と[一括runner](../run_network_similarity_optimization.py)に固定した。第6段階のprotocolと同じ最適化シード表・評価回数・反復数・探索用シミュレーションシードを参照し、**126件の最適化と20件の固定条件を別々のrunとして管理する**。元の3グラフについては固定条件のみを追加し、第6段階の54最適化runを再実行しない。`--dry-run`で146コマンド、追加7グラフ各20件、元3グラフ各2件を確認した。

観測グラフ4件の入力はGit管理対象外のため、`experiments/summer_2026/observed_network_inputs/20260922_v01_full.tar.gz`にまとめ、同ディレクトリの`.sha256`を作成した。gzip検査とSHA-256検査は通過済み。runnerは元の第6段階protocol、観測グラフ入力manifest、各入力ファイル、BA別実現の設定・辺・`comm.csv`のハッシュを本実行前に照合する。**Gitのcommit・pushだけでは観測グラフ入力は共用PCへ届かない**ため、アーカイブを別途転送して展開する。生成スクリプトとテストはGitに含める。

| 検査項目 | 結果 |
| --- | --- |
| 実行計画 | 最適化126件、固定比較20件、計146件 |
| 探索評価 | 7グラフ×3手法×6最適化シード×50評価＝6,300評価 |
| 固定比較 | 追加7グラフと元3グラフ×無介入・単純最大化＝20件 |
| 反復総数 | 最適化630,000、固定比較2,000、計632,000 |
| Macでの1反復スモークテスト | Brandeis99で無介入・ランダムサーチ1評価とも完了。約42秒・51秒（初期化込み） |
| 本実験 | **未実行**。共用PCへの入力転送、短いpilotと所要時間確認を経て着手 |

Macのスモークテストは一時ディレクトリに置き、正式な実験結果には混ぜない。時間はMac固有の初期化・入出力を含むため、100反復や共用PCの所要時間を単純比例で見積もらない。共用PCではまず密なFacebookグラフの固定条件1件を本実験IDで実行し、その`timing_sec`を確認してから全146件へ進む。途中停止した場合は同じID・同じGit commit・同じprotocolで`--resume`する。既存runが不完全な場合は黙って上書きせず停止する。

転送・展開後のドライラン例（共用PC）：

```bash
cd ~/cap-sn
EXPERIMENT_ID="$(date '+%Y%m%d_%H%M%S')_network_similarity_optimization_v01"
printf '%s\n' "$EXPERIMENT_ID" > "$HOME/cap_sn_network_similarity_id.txt"
.venv/bin/python run_network_similarity_optimization.py \
  --experiment-id "$EXPERIMENT_ID" --dry-run \
  > "$HOME/${EXPERIMENT_ID}_dry_run.json"
```

Macで生成した入力アーカイブのSHA-256は`56cf7fc30ee270ff5d7d098b25372f1ef30f8778b884e1a0ac35501c6eeb6f23`。展開先は`experiments/summer_2026/observed_network_inputs/`で、直下に`20260922_v01/`ができる。結果の分析では追加グラフ7件の探索点と2固定条件をまずネットワーク別に整理し、元3グラフの既存第6段階結果と比較する。ただし、今回の新規実行は単一探索用シードのみなので、良好領域の再現確認と構造的原因・未知シードでの効果検証は区別する。
